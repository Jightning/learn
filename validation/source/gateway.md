# Synthetic gateway source packet

This is a fictional project. Its numbers are sufficient to check arithmetic
and reasoning inside this evaluation. They are **not** evidence for any real
person's resume. Use source references S1–S4 in the submission.

## S1: Fixed-population replay

The team replayed the same fixed set of requests through a baseline path and a
gateway path. Input tokens are tokens sent to a model; output tokens are tokens
generated by it. “Provider tokens” below means their sum. A full-response
cache hit returns a previously approved response without calling a provider.

| Product | Requests | Baseline input tokens | Baseline output tokens | Gateway input tokens | Gateway output tokens | Full-response cache hits |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 1,000 | 1,200,000 | 200,000 | 720,000 | 120,000 | 400 |
| B | 1,000 | 1,000,000 | 100,000 | 170,000 | 17,000 | 830 |

For this replay, no other prompt or completion lengths changed among misses.
The token reduction for a population is `(baseline provider tokens - gateway
provider tokens) / baseline provider tokens`. “Up to” reports the maximum
product-level result, not the total across products. Do the arithmetic; do not
mistake a product-level result for the combined result.

Dollar cost is different. The baseline provider charges $2 per million input
tokens and $8 per million output tokens. The gateway may route misses to a
provider charging $0.50 and $2 respectively. Routing can reduce dollars with
identical token counts. It can also change token counts indirectly if prompts,
model outputs, or retry behavior change; that must be measured, not assumed.
Deferred batch processing can change price and latency without itself removing
tokens. Shared context or fewer duplicate calls would be a separate mechanism.

## S2: Proposed request path

`client -> authenticated gateway -> policy check -> tenant-scoped cache lookup
-> model selection -> provider -> response validation -> telemetry -> client`
is the intended flow. Cache hits skip model selection and provider calls but
still pass authorization and response policy checks. A gateway adds an extra
hop and creates a shared failure point. If the provider fails, a fallback may
increase reliability but also change cost, latency, or answer quality.

## S3: Cache boundary

A full-response cache key must include tenant identity, content after safe
normalization, model/policy version, and response-affecting parameters. Omitting
tenant identity can leak another customer's response. Omitting version or
parameters can return a stale or semantically wrong response. Never cache
private content across tenants merely because the prompt text matches.

This is distinct from a transformer's key-value (KV) cache. A KV cache keeps
past attention keys and values inside one generation. It avoids recomputing
those past projections but still attends over a growing prefix: attention work
for the next token is not constant in context length. It consumes memory that
grows with context length. Do not use KV-cache behavior to explain the replay's
full-response cache hits.

## S4: Resume-style claim

A fictional candidate's bullet reads: “Reduced model token usage by up to 83%
through a shared request gateway with routing, caching, and opt-in batching.”
The replay in S1 demonstrates how an 83% product-level reduction **could**
arise. The packet does not establish that the fictional candidate actually
used this replay, what their real baseline/window was, or how much each
mechanism contributed. A truthful interview answer must distinguish a
supported mechanism from a historical claim needing the owner's records.

An interviewer may ask: Was 83% typical or the maximum? Which population and
denominator? Was the baseline the same requests? Were cache hits valid? What
changed in dollar cost? What did the gateway cost in latency, reliability, and
maintenance? What evidence would falsify the claimed causal story?
